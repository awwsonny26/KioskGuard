# Межі KioskGuard без RTOS

Поточні стендові дані і негативний результат Flash наведено в [метриках](metrics/lab3-observed-20261101/README.md). Частина нижчих обмежень є аналізом коду або host-моделі, а не фізичним вимірюванням. Гіпотези не є результатами ЛР4.

## 1. Невитіснюване стирання flash

Симптом: одна erase у `Platform/nvflash.c` не повертає керування до HAL_FLASHEx_Erase. У цей інтервал super loop не опитує PIR/IMU й не розбирає RX. Доказ структури: один спільний стек та синхронний HAL. Host cadence перевіряє наслідок модельного інтервалу 65 мс: два пропущені слоти 20 мс і джиттер 45 мс. Це модель, не виміряний час flash. Datasheet DS13867 Rev4 потрібен для меж фізичного стирання, Wokwi не доводить його час.

Без ОС: виконувати erase завчасно, переносити критичні обробники та потрібний код у RAM, забезпечити запас живлення. Це потребує окремої верифікації лінкування і flash stalls. ОС: вищий пріоритет сенсорів допоможе лише коли MCU може виконувати код під час flash busy. Саме витіснення не усуває stall однобанкової flash. Ціна: стеки, RAM, IRQ та flash-координація. Гіпотеза ЛР4: за RAM-resident критичного шляху зменшити додаткову затримку PIR під erase до 25 мс; без цього поліпшення не прогнозується.

## 2. Скінченна пропускна здатність UART

Симптом: 127 байтів RX при 115200 8N1 вистачає приблизно на 11,02 мс без споживання; черга EVENT має 16 записів. Доказ: розміри `runtime.c`, `kiosk.h`, host overflow test ЛР2, арифметика 127×10/115200. Це розрахунок, не знайдена експериментальна точка зламу. Потік command може створювати події швидше за передачу розгорнутих рядків.

Без ОС: flow control, стислий протокол, окремі черги відповідей та журналу, більші буфери коштом RAM. ОС: черга команд з пріоритетом обробника, backpressure та облік відмов приймання. Пріоритети не збільшать фізичні 115200 біт/с. Ціна: RAM черг, можливе блокування producer. Гіпотеза ЛР4: за того самого потоку зменшити queue_drop, зберігши явно обмежену чергу; ціль нуль втрат визначити після пошуку межі ЛР3.

## 3. Справедливість між відповідями й діагностикою

Симптом: `output` обслуговує audit status та багаторядковий stats перед EVENT; пріоритет діагностичних відповідей над EVENT може відкладати події при повторних запитах. Межу потоку не виміряно. Доказ: порядок гілок `runtime.c`. Верхня межа FR-08 у цьому випадку не доведена. Це наслідок кооперативного арбітражу одного UART, не дефект електричної лінії.

Без ОС: квоти по класах повідомлень, заборона перезапуску активного stats, окремий snapshot. ОС: пріоритетна черга відповідей і задача TX з обмеженою порцією. Ціна: інверсія пріоритетів біля UART mutex та додаткова пам'ять. Гіпотеза ЛР4: повний ACK service ≤200 мс у тому самому S3, не жертвуючи сенсорними строками. Механізм справедливості можна реалізувати і без ОС.

## 4. Вікно недовговічних даних і обмежена історія

Симптом: dirty RAM totals ще не є flash. Журнал має 32 слоти на сторінку; під час нового snapshot можливе об'єднання кількох подій. Доказ: host тести обриву в 65 точках запису й 2113 точках ротації, тест нової події під час запису. Вони доводять відновлення цілої попередньої/нової контрольного запису для моделі з однобайтовими обривами, а не фізичну поведінку brownout/ECC.

Без ОС: синхронний commit кожної події збільшить блокування та знос; зовнішня FRAM змінить апаратну частину й потребує нового PRD. ОС: окрема задача сховища та bounded queue відокремлюють відповідальність. Ціна: backlog RAM та стан синхронізації. ОС не перетворює незавершений commit на довговічний. Гіпотеза ЛР4: виміряти p99 event→commit, зменшити його щонайменше на 20% без збільшення кількості erase; zero-loss при вимкненні живлення не обіцяється.

## 5. Місце коду й стек обмежують подальше розділення

Симптом: після резерву flash лишилося 28 КіБ; перша збірка без LTO перевищила цей регіон на 1744 байти. Попередній build без LTO перевищив регіон; LTO та -Os дали придатну збірку. Точний запас поточного образу треба визначати за його map. Стек усіх шляхів спільний; окремі стеки ще не виділяються.

Без ОС: скоротити текстовий протокол, відокремити діагностичну збірку, контролювати map та глибину викликів. ОС: простіший поділ задач, але додасть kernel flash і кілька стеків. Ціна може перевищити доступний запас; MCU автоматично не змінюється. Гіпотеза ЛР4: спершу перевірити, чи мінімальна конфігурація RTOS взагалі лінкується у 28 КіБ та 12 КіБ RAM; окремо виміряти мінімум RAM на стеки. Це умова експерименту, не гарантія.

## 6. Межа часового джерела

Поточний кандидат планує за SysTick з кроком 1 мс і вимірює короткі ділянки 16-бітним TIM3; виміряна тривалість включає переривання й очікування. `CLOCK_CHECK` перевіряє прогрес грубого часу SysTick, а не роботу TIM3: напис `CLOCK_UNSUPPORTED TIM3` не є доказом перевірки TIM3. Окрема 30-мс проба та VCD підтвердили роботу таймера у досліджених умовах, але безперервного контролю його справності в прошивці немає. Є спостережені піки stack/heap, але повний CPU/WCET не доведено. GPIO-маркери дають іншу точку спостереження, але Wokwi не є незалежним фізичним вимірювачем. Для ЛР4 потрібні окремий облік ISR та повторення VCD; ціна — накладні витрати та додаткова пам'ять.

## Що варто зберегти без ОС

Один стек, статичні буфери, відсутність malloc у власному коді, явний порядок задач і відсутність context switch спрощують перевірку. Це властивості реалізації. Перевагу за швидкодією, стартом або енергією ще не виміряно, тому числової переваги над RTOS тут немає.
